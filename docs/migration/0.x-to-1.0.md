# Migration guide — 0.x previews to 1.0

> **Goal**: move an existing OgonGo 0.x project to the first stable
> 1.0 release. `ogon update` automates the mechanical steps and
> reports the manual ones.

This page covers, in order: **what**, **when**, **quickstart**, **config**,
**test**, **prod**, **escape**, **troubleshoot** (DOC-018).

---

## What

`ogon update` performs AST-based code migrations, config schema
migrations, infra diffs, and DB migration planning. The flow:

1. Read `ogon.json` (the framework version your project pins).
2. Compare against the latest stable release.
3. For each breaking change: emit a codemod (mechanical) or a
   documented manual step (when the change is semantic).
4. Apply codemods; print the manual steps with docs links.
5. `--diff-only` prints the plan without touching anything.

Every breaking change ships a codemod or a documented manual step
(DX-M14, OGON-VER-001).

## When

Run `ogon update`:

- before bumping the framework version in `go.mod`;
- when a new minor is released and you want to ride it;
- when a deprecation window closes (12 months minimum, Part XIX.5).

Do **not** run `ogon update`:

- in CI on every push — it is a project-level operation, not a CI step;
- without committing your working tree first (so you can `git reset
  --hard` if the codemod is wrong).

## Quickstart

```bash
# 1. pin the new version
go get github.com/OgonFrameworks/ogon.go@v1.0.0

# 2. plan
ogon update --diff-only
# -> codemod: rename Context.Logger() to Context.Log() (mechanical, 12 sites)
# -> manual:  auth.Session.MaxAge moved to auth.Session.Cookie.MaxAge (1 site: ogon.yaml)
# -> db plan: no schema changes

# 3. apply
ogon update --yes
# -> applied codemod: 12 sites renamed
# -> manual step: edit ogon.yaml (auth.Session.MaxAge -> auth.Session.Cookie.MaxAge)
# -> see docs/migration/0.x-to-1.0.md#session-maxage

# 4. verify
ogon check
ogon test
```

## Config

`ogon update` reads `ogon.json` (the framework version pin) and
`go.mod`. No additional config is needed.

## Test

`ogon update --diff-only` is the test. It exits 0 if the plan is
empty, non-zero if there are pending changes. CI gates on this for
the framework's own dogfooding repo.

The `test.MigrationCorpus` (in the `test` package) is a set of seeded
0.x projects that `ogon update` must bring to 1.0 cleanly. AT-015.

## Prod

After `ogon update`:

1. `ogon check` — config valid, gen up-to-date.
2. `ogon test` — all tests pass.
3. `ogon build` — binary builds.
4. `ogon deploy --cloud aws --rollback` — ship with auto-rollback.

The DB migration plan (if any) is applied via `ogon migrate run` in
the migration Job, **not** at boot.

## Escape

- **Skip the codemod**: `ogon update --skip-codemod <name>` skips a
  specific codemod; you do the rename by hand.
- **Bring your own codemod**: drop a Go file in `tools/codemods/`
  implementing the `update.Codemod` interface; `ogon update` will
  pick it up.
- **Roll back**: `git reset --hard <pre-update-sha>` and `go get
  ogon.go@<old-version>`. The framework never mutates the DB during
  `ogon update`.

## Troubleshoot

| Symptom                                | Fix                                                            |
|----------------------------------------|----------------------------------------------------------------|
| `ogon update` reports 0 changes         | You are already on the latest stable; check `ogon --version`.  |
| Codemod fails to apply                  | Read the error; revert with `git restore`, apply by hand.      |
| Manual step link is broken              | File a docs bug; the link is auto-generated from the changelog.|
| `ogon test` fails after update          | The codemod was incomplete; read the diff and finish by hand.  |
