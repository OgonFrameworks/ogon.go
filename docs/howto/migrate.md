# How-to — Run database migrations safely

> **Goal**: generate, apply, review, and roll back database migrations
> without losing data. Understand the destructive-op gate
> (`OGON-M0001`) and how to override it safely.

This page covers, in order: **what**, **when**, **quickstart**, **config**,
**test**, **prod**, **escape**, **troubleshoot** (DOC-018).

---

## What

OgonGo's migration engine is `ogon migrate`. It takes the AST of your
`models/*.go` and the live DB schema, diffs them, and emits reversible
SQL. The four subcommands:

| Subcommand     | Effect                                                        |
|----------------|---------------------------------------------------------------|
| `ogon migrate diff`    | Print pending changes (no writes).                     |
| `ogon migrate create`  | Write a new migration pair (`*.up.sql` + `*.down.sql`). |
| `ogon migrate run`     | Apply pending migrations (in a tx where the driver supports DDL). |
| `ogon migrate rollback`| Roll back one step, or `--to <version>`.               |
| `ogon migrate status`  | What's applied; what's pending.                         |

Destructive operations (`DROP TABLE`, `ALTER ... DROP COLUMN` with data
loss, `TRUNCATE`) trigger `OGON-M0001` (exit 4) and require `--yes`.

## When

Use `ogon migrate`:

- after editing a model's `ogon:` tags;
- in CI before `ogon deploy` (run `diff` -> `run`);
- when rolling back a bad deploy;
- when seeding a fresh DB.

Do **not** use `ogon migrate`:

- on the production DB at boot — auto-migrate is explicitly disallowed
  in prod (Part XX). Use `ogon migrate run` in a CI step or a
  migration Job instead.

## Quickstart

```bash
# 1. edit the model
$EDITOR models/Post.go

# 2. see what changed
ogon migrate diff
# -> add column published_at timestamptz

# 3. write the migration pair
ogon migrate create add_published_at
# -> migrations/0007_add_published_at.up.sql
# -> migrations/0007_add_published_at.down.sql

# 4. apply
ogon migrate run

# 5. roll back if you change your mind
ogon migrate rollback
```

### Destructive op gate

Drop a column with data:

```bash
ogon migrate diff
# -> OGON-M0001: migration unsafe (drop column 'body' on 'posts' will lose data)
# -> remedy: pass --yes to confirm, or rename the column instead.

echo $?
# 4
```

Override (after due diligence):

```bash
ogon migrate run --yes
```

## Config

`ogon.yaml`:

```yaml
database:
  driver: postgres
  url_env: OGON_DB_URL
  migrate:
    auto_apply: false         # never in prod (Part XX)
    dangerous_requires_yes: true
    transactional: true       # pg: yes; sqlite: partial
```

`ogon.<env>.yaml` can override per-env. The dev overlay typically sets
`auto_apply: true` so `ogon dev` keeps the schema in sync while
coding.

## Test

The migration engine ships with three test helpers (in the `test`
package):

| Helper                       | What it checks                                                |
|------------------------------|---------------------------------------------------------------|
| `test.MigrationUpTest`       | Every `*.up.sql` applies cleanly to a fresh DB; `*.down.sql` rolls it back. |
| `test.OpenAPIDriftTest`      | The OpenAPI spec generated from the models matches the spec checked in. |
| `test.TSTypeDriftTest`       | The TypeScript types generated from the models match the spec. |

Drop them into `migrations_test.go`:

```go
// SPDX-License-Identifier: MIT
// Copyright (c) 2026 OgonFrameworks. All rights reserved.
//
// Migration drift tests.

package migrations

import (
    "testing"

    "github.com/OgonFrameworks/ogon.go/test"
)

func TestMigrations(t *testing.T) {
    test.MigrationUpTest(t, "migrations/")
    test.OpenAPIDriftTest(t, "models/", "api/openapi.yaml")
    test.TSTypeDriftTest(t, "models/", "ui/types/models.ts")
}
```

AT-024 ("Migration with `DROP TABLE` blocks without confirm; exit 4")
runs against the migration engine in CI.

## Prod

```bash
# in a CI step (NOT at boot):
ogon migrate status
ogon migrate diff
ogon migrate run --yes       # only if diff was reviewed

# or as a k8s migration Job (generated by `ogon infra gen k8s`):
kubectl apply -f infra/k8s/migration-job.yaml
kubectl logs job/migration-1.0.0
```

The migration Job runs once per release; the main Deployment waits for
it to complete before rolling. This is the only safe prod path.

## Escape

- **Raw SQL**: drop a hand-written `.sql` file in `migrations/`; the
  engine runs it as-is (no diff).
- **Skip the engine**: set `database.driver: none` and `ogon build`
  will not emit migrations.
- **External tool**: `flyway`, `golang-migrate`, `liquibase` — all
  work because OgonGo migrations are plain SQL files with a standard
  `V<n>__<name>.up.sql` naming convention.

## Troubleshoot

| Symptom                                           | Fix                                                          |
|---------------------------------------------------|--------------------------------------------------------------|
| `OGON-M0001: migration unsafe` (exit 4)           | Read the destructive-op detection line; pass `--yes` or rename the column. |
| `OGON-M0002: migration partial tx` (sqlite)        | SQLite cannot run DDL in a tx; the engine runs it statement-by-statement. |
| `ogon migrate rollback` does nothing              | The down migration is missing; write one with `ogon migrate create --reverse`. |
| `MigrationUpTest` fails                            | A previous migration left the schema dirty; `ogon db reset` and retry. |
| `ogon migrate diff` shows phantom changes          | Your local DB is ahead of the migrations; commit them or roll back. |
